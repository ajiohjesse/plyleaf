# Engine spike (D-006)

Date: 2026-10-31 · Milestone: M1 · Decision: [D-015](../DECISIONS.md)

**Question.** Which PDF engine(s) should Plyleaf ship: MuPDF.js alone, MuPDF.js plus pdf-lib for light structural
tools, or pdf.js / PDFium for rendering?

**Answer.** Use **MuPDF.js alone**, in a Web Worker. It was the fastest renderer in all three browser engines, it was
fastest at merge and rotate, and it is the only candidate that also covers the later milestones (redaction, flatten,
encryption, repair, undo journal, text search). Its cost is the download: 3.5 MB Brotli on the first use of any tool,
against 1.6 MB for PDFium. That's a one-time cost (the files are immutable and cached, and offline-cached from M9), and we
can hide most of it by starting the download as soon as the user reaches for a file.

## Candidates

| Engine | Version | Licence | What it does |
|---|---|---|---|
| MuPDF.js (`mupdf`) | 1.28.1 | AGPL-3.0 | Render, edit, annotate, redact, encrypt, repair, convert. WASM. |
| PDFium (`@embedpdf/pdfium`) | 2.15.1 | MIT + Apache-2.0 | Chrome's engine in WASM, with EmbedPDF's extensions (annotations, forms, redaction, save). |
| pdf.js (`pdfjs-dist`) | 6.4.299 | Apache-2.0 | Firefox's renderer in JS, plus `extractPages` for merging. No general editing. |
| pdf-lib (`@cantoo/pdf-lib`) | 2.11.1 | MIT | Structural edits and drawing in JS. No renderer. |

## Method

- **Reference files** (generated by `bench/engine/make-fixtures.ts` with a seeded PRNG, so they're licence-clean and
  reproducible; not committed because they're 80 MB):
  - `text.pdf`: 12 pages of text in Helvetica (non-embedded standard font), 40 KB.
  - `scanned.pdf`: 100 greyscale "scans" (text pages rendered at 150 dpi with paper tone and noise, JPEG q70), 28 MB.
  - `mixed.pdf`: 42 pages repeating text, a vector chart (6,000 path points, 300 circles) and a full-page 300 dpi RGB
    photo (JPEG q90), 52 MB.
- **Harness** (`bench/engine/`): a Vite page loads one engine on demand and runs the suite; `run.ts` builds it, serves the
  production build and drives it with Playwright: 3 runs per engine per browser, each in a fresh browser context (empty
  HTTP cache). Tables show medians.
- **Operations**: open (parse + page count); render page 1 as a 200 px-wide thumbnail and at 150 % zoom; render every page
  as a thumbnail; merge all three files (154 pages) and save; rotate every page of `mixed.pdf` and save (full rewrite).
  Every merged and rotated output was reopened and its page count checked; all passed. Rendering includes painting
  the result into a canvas. pdf-lib can't render, and pdf.js can't rotate and save.
- **Machine**: Windows 11 desktop, headless Playwright browsers: Chromium 156, Firefox 157, WebKit 27.2. Everything ran on
  the main thread. The product will run the engine in a worker, which adds the same small transfer cost to every
  candidate.
- **Download size**: the files each engine actually requested during init, measured from the production build and
  compressed with gzip -9 and Brotli.
- **Memory**: WASM linear memory only grows, so its size at a point in the run is the peak up to then. JS memory comes
  from `performance.measureUserAgentSpecificMemory()` in Chromium; it covers the page and its workers but not WASM
  memory, and it isn't forced to garbage-collect, so treat those figures as rough.

Re-run: `node bench/engine/make-fixtures.ts`, then `node bench/engine/run.ts [runs] [browsers]` and
`node bench/engine/report.ts bench/engine/results/<date>.json`. Raw results: [bench/engine/results/2026-10-31.json](../../bench/engine/results/2026-10-31.json).

## Findings

1. **MuPDF.js was the fastest renderer in every browser** for bulk thumbnails, the case the Organize workspace hits
   most. PDFium was close in Chromium and WebKit but 7× slower in Firefox (17.6 s for the 100-page scan). pdf.js was
   7–11× slower in WebKit (22.5 s). Either one would make one of our target browsers feel broken.
2. **MuPDF.js was also fastest for structural edits** (merge 133–142 ms, rotate 43–72 ms in all browsers). pdf-lib
   took about 2× as long for merge and rotate, and it holds the most JS memory afterwards.
3. **Every tool needs a renderer anyway**, because each one shows page thumbnails once a file is dropped. Any tool that
   used pdf-lib would load MuPDF.js too, so "MuPDF.js + pdf-lib" adds bytes and a second code path but saves nothing.
4. **Download is MuPDF.js's real cost**: 3.5 MB Brotli against PDFium's 1.6 MB. Mitigations: (a) start the download
   when the user opens the file picker or drags a file over the page, so most of it overlaps with choosing a file; (b) the
   files are content-hashed and served `immutable`, so it's a one-time cost per version; (c) M9's service worker keeps it
   for offline use. The page itself still ships no engine code (P6).
5. **Memory is dominated by the WASM heap**, which never shrinks. Opening the 52 MB file and rendering its thumbnails
   took MuPDF.js to 226 MB, and merging 80 MB of inputs took it to 469 MB. PDFium behaves the same. The engine worker
   should be **recycled** (terminated and restarted) after a large job or when it's idle, which returns the memory, and
   the memory-limit UX should be based on input size.
6. **Feature coverage**: MuPDF.js already exposes what M4–M7 need: `applyRedactions` (true redaction of text, images
   and line art), `bake` (flatten), AES-256 encryption and permissions on save, `wasRepaired`, garbage collection and
   stream compression on save, an undo/redo journal, structured text and search, and a `DocumentWriter` for building
   PDFs (images → PDF). PDFium via EmbedPDF covers much of this too (annotations, forms, redaction, encryption), but its
   save has no clean-up options (garbage collection, recompression), and it's the slower choice in Firefox.
7. **Licence**: MuPDF.js is AGPL-3.0, which matches our licence (D-004). Nothing else is needed.

## Decision

- Ship **MuPDF.js as the only PDF engine**, behind the typed worker API (next M1 item).
- Don't ship pdf-lib, pdf.js or PDFium. They stay as dev dependencies only so the benchmark can be re-run.
- Revisit if a later tool turns out to need no rendering, if MuPDF.js's WASM grows a lot, or if the M3 image-compression
  or M7 OCR work shows a gap. Ghostscript WASM for "extreme" compression and PDF/A is still planned separately
  (STRATEGY §6).

## Caveats

- Desktop machine; phones will be slower across the board. The ranking held in all three browser engines, so it's
  unlikely to flip on a phone, but mobile numbers get checked when thumbnails land.
- Init times are from localhost, so they show compile cost, not network. The 10 Mbit/s column estimates the network cost.
- Rendering ran on the main thread with headless browsers (no GPU), which may handicap pdf.js, the only canvas-based
  renderer. It doesn't explain the gaps in finding 1.
- Check Cloudflare serves `.wasm` compressed when the worker ships. The Brotli figure assumes it does.
